# Performance report

Measured with `benchmarks/perf/run_perf.py` (tables rendered by `benchmarks/perf/report.py` from
`build/perf_results.json`). Everything below was run for real on the machine described at the end; nothing is
extrapolated. **No machine learning model is involved**: the engine is regex/Hyperscan/Gitleaks rules plus
Presidio's deterministic recognizers.

## Setup

* **Host**: 4 logical CPUs (Intel Xeon @ 2.10 GHz), 15.7 GB RAM, Linux, a shared cloud VM (expect noise; P99/max
  values include scheduler jitter). The load generator (`dlp bench`) runs on the **same machine** as the server, so
  server numbers are conservative: the client takes CPU too.
* **Binaries**: `cargo build --release` (Rust 1.97), Hyperscan 5.4.2 as prefilter for keyword-less rules.
  Ruleset: 256 enabled rules (223 imported Gitleaks + built-ins).
* **Policy**: `audit-only` for the HTTP runs (`fail_open_with_audit`, so an overloaded NLP service degrades the
  response instead of blocking it); in-process runs use the default engine settings.
* **Input**: synthetic text of the given size containing a mix of entities (phones, IDs, e-mail, keys), generated by
  the benchmark itself. The same text shape is used for every row.
* **NLP service**: Presidio recognizers only, 2 worker processes (`DLP_NLP_WORKERS`, default `cpus/2`), chunked
  analysis (8 000 chars, 64 overlap), 25 s budget per call. CPU % is summed over the service's processes
  (100 % = one core); RSS is the sum over processes.
* **Concurrency** is the number of concurrent client threads/connections (1, 10, 50, 100); **req/s** counts HTTP
  requests (or in-process calls), **items/s** counts texts (batch requests carry 16 or 64 texts).
* Latencies are per request, end to end (client-observed for HTTP).
* Soak: 600 s rules-only + 240 s with all detectors. Hot reload: a reload every 3 s during 30 s of load.

## Reading the numbers

**Rules path (the product's main path).**
* In-process, one thread: **~12 000 req/s at 100 B, ~5 300 req/s at 1 KB, ~600 req/s at 10 KB, ~62 req/s at
  100 KB, ~1.2 req/s at 1 MB** (≈ 0.9 s for 1 MB, i.e. roughly 1.1 MB/s per core with all 256 rules and masking).
  Throughput per byte is roughly constant from 10 KB upward, so cost is linear in input size (no ReDoS cliff: the
  regex engine is linear-time and rule size/complexity limits are enforced at compile time).
* 10 threads reach ~19 500 req/s for 1 KB texts on 4 cores; going to 50/100 threads does not add throughput and
  only raises tail latency (P99 52 ms / 127 ms), as expected on 4 cores.
* **sanitize costs about the same as detect** (17 303 vs 18 145 req/s at 1 KB, 4 threads) — masking is a single
  linear pass over the already-found spans.
* Over HTTP, rules only: **~1 050–1 150 req/s with one client, ~5 100–5 500 req/s with 10–50 clients**, P99 under
  5 ms at 10 clients, 22 ms at 50 and 73 ms at 100 clients. Server CPU saturates at ~300 % (3 of 4 cores, the
  rest is the load generator). Batching helps: 64 × 1 KB texts per request give ~7 000 texts/s.
* **Memory**: server RSS 58 MB idle → ~280 MB after the 1 MB and batch cases → plateau ~519 MB during the 10-minute
  soak with hot reload (no growth over the soak; a reload keeps old and new compiled rule sets alive briefly).
* **Soak (600 s, 10 clients)**: 0 errors, 0 degraded responses, stable throughput (~4 050 req/s), P99 6.9 ms.
* **Hot reload every 3 s under load**: 0 errors, throughput ~3 750 req/s (about 7 % below the separate 10-minute run without reloads), P99 7.8 ms,
  max 86 ms. A reload of the full 256-rule set (compile) takes **≈ 1.4–1.6 s** wall time in the background; requests
  keep being served by the previous rule set until the swap, so no request waits for it.
* **Rule compile time**: ~1.56 s for the 256 enabled rules (`compile_ms` of the reload endpoint; includes the
  regex builds and the Hyperscan prefilter database).

**NLP path (Presidio recognizers).**
* Presidio's recognizers are pure Python and CPU-bound (≥ 90 % of the time is libphonenumber matching), so
  they are by far the slowest component: **~3.9 ms at 100 B, ~12 ms at 1 KB, ~137 ms at 10 KB, ~1.4 s at 100 KB,
  ~14 s at 1 MB** (single client). Throughput is limited by the number of worker processes:
  ~165 texts/s at 10 clients with 2 workers (≈ 190 % NLP CPU).
* With **50 clients** the service saturates (≈ 114 req/s, mean 434 ms). With **100 clients the NLP gate sheds
  load and the engine answers from the rules alone: 60 116 responses were marked `degraded:true`** (the 2 982 req/s in
  that row are therefore mostly *rules-only* responses and **must not be read as NLP throughput**). Nothing was
  reported as clean without having run: the degradation is explicit in each response and the audit log, and a policy
  with `presidio` in `mandatory_detectors` (e.g. `strict`) blocks instead.
* A 1 MB text takes ~14 s through the NLP service (within its 25 s budget). Larger or slower inputs hit the budget
  and are reported as a detector error (degraded / blocked per policy), never hang a worker.
* If you do not need Presidio's international phone/IBAN/crypto recognizers, run without `--nlp-url`: the rules
  path above has no NLP dependency and detects CN phones, IDs, cards, e-mail, secrets, etc. by itself.

## Fixes found by this benchmark (kept for traceability)

1. **Presidio was superlinear in text length** (10 KB 0.25 s but 100 KB 7.5 s and > 120 s for 1 MB, which also
   stalled every later request because the service kept working after the caller timed out). Fixed by chunked
   analysis with a time budget: 100 KB 7.5 s → 1.4 s, 1 MB > 120 s → ~14 s.
2. Presidio ran the language-independent recognizers twice on mixed zh/en text and ran phone matching on texts
   with fewer than 7 digits. Both removed (≈ 2× on mixed text).
3. uvicorn's multi-process mode left TCP_NODELAY off, adding a 40 ms Nagle/delayed-ACK stall to every keep-alive
   request (44 ms vs 2.8 ms). The service now owns the listening socket and sets TCP_NODELAY.

## Not measured / caveats

* No Windows numbers (the Windows build was only smoke-tested under wine). No GPU (none used).
* The load generator shares the 4 cores with the server and the NLP service.
* The benchmark text is synthetic; real text with fewer matches is faster, text full of digit runs is slower in the
  NLP service.
* Idle-state model load numbers are trivial now: the NLP service starts in < 1 s (no model weights).
* Network, TLS termination and authentication proxies are not included.
